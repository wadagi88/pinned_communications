01

The SMS journey

Every moment in order, grouped, and the channel that carries it. Highlighted rows cost an SMS — 3 SMS on a business door delivery · 4 on an individual send · 2 to collect — and everything unhighlighted is a deliberate decision not to spend one. The arrow on the right of each row jumps to the copy.

Three SMS on a business door delivery, four on an individual send, two to collect

The count is not one number, and pretending it was is how this site got it wrong. What is constant: one message at creation, whose verb is set by the entry state — confirm, choose, or track and confirm — and one carrying the code, whenever the last of the three gate rails clears. An individual send adds a message when the parcel actually leaves the sender. A door delivery adds the rating, once per receiver ever. Free collection gets neither.

02

Which message fires, and when

The first SMS is not an announcement, it is an instruction — and the instruction depends on what the person has to do when the link opens. The dev page derives that from one field: receiver_data.sender_address. If the sender supplied an address, the receiver confirms it and there is no choice and no distance screen. If not, they choose, and for pay-on-delivery and covered trips the trip is booked the moment they type an address. An individual's receiver never reaches that page at all — they get the tracker, and the ask is track it and confirm your address. Three verbs, eleven cases, and in every one of them the same two messages.

01

The verb of the first sentence is the entry state

Confirm when the sender gave us an address. Choose when they did not. Track and confirm for an individual send, which lands on /track/<token> and never on the choice page. Getting this wrong is not a tone problem: a receiver told to “collect it free, or have it delivered” opens a page with neither option on it.

02

Money is a trailing clause, never the lead

On a confirm journey the primary action is identical across all three fee modes, so the fee goes last and pay-now reads like the covered case rather than like a bill. The page already does this; the SMS has to match it or the two read as different companies.

03

One SMS when the parcel is created

Whoever created it, exactly one SMS goes out at creation. The entry state and the money change what it says. Nothing changes the count. This is the only part of the old “two messages” rule that survived reading the code.

One person sending to another, settled and paid in the sender wizard. They never reach the choice page. Receiver::DropNotifier sends them to /track/<token>, which opens on an address confirm and then runs live tracking. The address is already set, so the only variable is how the parcel gets out of the sender's hands — and the first sentence has to say which, in the future tense.

03

The gate

The doorstep code is the only thing Pinned withholds from anybody, so the rule behind it is worth stating exactly. It is not a property of the fee mode — pay_now + goods and covered + goods hold the code too — and the three things that hold it are released by three different parties, which the copy must never blur.

The rule, verbatim

code_held? = trip_fee_due? || goods_owed? || extension_payment_due?, from Parcel::FeeMode. Three conditions, any one of which is enough. A journey that trips two of them has to satisfy both before a single character is sent.

Rail one · the trip fee releases itself

cod_flag? && !business_covered? && !fully_paid?. An M-Pesa STK the receiver starts on the page; it clears when payment_confirmed_at is set. Nobody approves it, and the runner never touches money. This is the rail the copy already describes correctly.

Rail two · the goods are released by the seller

goods_enabled? && goods_confirmed_at.nil?. Goods are paid on the seller's own rails and Pinned cannot see that money. The receiver files a goods_payment_claimed interaction and the seller releases the code from the host portal. The receiver is waiting on a person, and the copy has to say so rather than implying a machine is checking.

Rail three · an unpaid relocation holds it too

extension.open? && extension.payment_due?. A pay-now receiver who has been quoted a relocation fee and not yet paid it has their code held — on a parcel that may have had nothing owed ten minutes earlier. This site missed it entirely, which is why C9's line “your handover code stays locked until this clears” is a statement of fact and not a flourish.

Three release events, one message

parcel.handover_code_released fires once, whichever rail cleared last, and handover_code_ready / handover_code_ready_covered carry the code. It is still one message, and it still carries only the code.

One disclosure path, for every channel

Every disclosure of the doorstep code goes through disclosable_handover_code — page, SMS and JSON alike. In the helper's own words: if the raw column reaches a client while held, the hold is cosmetic.

The pickup code is never gated

virtual_host_otps.otp_code is a different object and is never held — in Parcel::FeeMode's own comment, a runner must always be able to collect from the host branch regardless of what the receiver owes. Two codes, two words, never used interchangeably.

04

What they are here for

The person the parcel is for. Often has never heard of Pinned before the first SMS.

The job they hire Pinned for

Get the parcel without rearranging their day.

Every message on this page is judged against that sentence. If it does not help with it, or protect it, it should not be sent.
